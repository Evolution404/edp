# EDPOpen FDA Raw Broker PoC — 2026-08-29

## Goal

Validate a persistent raw USB permission model for macOS 26 where Full Disk Access (FDA) is granted once to a stable privileged broker, after which App restarts, broker restarts, USB unplug/replug, and `diskN` changes do not require `authopen`, administrator prompts, or Touch ID.

The PoC intentionally does **not** integrate with the production EDPOpen raw-device path.

## Safety constraints

The probe only accepts a numeric whole-disk number and constructs `/dev/rdiskN` internally. It performs:

1. Disk Arbitration validation: whole disk, external, USB.
2. IOKit validation: BSD media has an `IOUSBHostDevice` ancestor.
3. `open(path, O_RDWR | O_CLOEXEC)`.
4. `fstat(fd)` and character-device validation.
5. `close(fd)`.

The probe does not call `read`, `pread`, `write`, `pwrite`, format, partition, erase, or change media contents.

## Baseline: root without FDA

Real USB at `/dev/disk8`.

Validated device:

- Disk Arbitration: `whole=true`, `internal=false`, `protocol=USB`
- IOKit: `IOUSBHostDevice` ancestor present

Root probe result before FDA:

```text
PROBE_ID=com.evolution404.edpopen.rawbroker.poc
EUID=0
PATH=/dev/rdisk8
VALIDATION=DA whole=true internal=false protocol=USB ...; IOKit ancestor=IOUSBHostDevice
DIRECT_RAW_OPEN=FAIL errno=1 Operation not permitted
```

TCC logged `kTCCServiceSystemPolicyAllFiles` denial for the broker path itself.

## FDA enabled once

After manually enabling Full Disk Access for the fixed broker executable, the mounted volume first caused `O_RDWR` to return `EBUSY`, which is a mount-state issue rather than TCC denial.

After temporarily unmounting the whole disk, the same broker succeeded:

```text
PROBE_ID=com.evolution404.edpopen.rawbroker.poc
EUID=0
PATH=/dev/rdisk8
VALIDATION=DA whole=true internal=false protocol=USB ...; IOKit ancestor=IOUSBHostDevice
FSTAT_CHAR_DEVICE=OK rdev=16777244
DIRECT_RAW_OPEN=OK
```

The disk was immediately remounted afterward.

## LaunchDaemon new-process validation

PoC LaunchDaemon:

`system/com.evolution404.edpopen.rawbroker.poc`

A normal-user trigger caused system launchd to start a new root process. No `sudo`, `osascript`, `authopen`, administrator prompt, or Touch ID was used.

Result on `disk8`:

```text
runs = 1
last exit code = 0
EUID=0
PATH=/dev/rdisk8
DIRECT_RAW_OPEN=OK
```

TCC attribution remained the broker executable itself.

## USB unplug/replug and diskN change

The USB was physically removed. Five 1 MiB RAM disk images occupied `disk4` through `disk8`. The real USB was then reinserted and enumerated as `disk9`.

Without changing FDA, reinstalling the broker, or using administrator authorization, the same LaunchDaemon was triggered again:

```text
runs = 2
last exit code = 0
EUID=0
PATH=/dev/rdisk9
VALIDATION=DA whole=true internal=false protocol=USB ...; IOKit ancestor=IOUSBHostDevice
FSTAT_CHAR_DEVICE=OK rdev=16777241
DIRECT_RAW_OPEN=OK
```

The RAM disks were detached after the test. The real USB remained mounted as `disk9`.

## Conclusion

The required permission model is validated on this Mac:

- `authopen` is not needed for ongoing raw access.
- Root alone is insufficient without FDA (`EPERM`).
- A stable, certificate-signed privileged broker with FDA can directly open `/dev/rdiskN` read/write.
- FDA persists across broker process exit and relaunch.
- A system LaunchDaemon can start the broker without user authorization.
- FDA persists across physical USB unplug/replug and `diskN` changes.
- TCC attribution is to the broker itself, not Terminal, AppleScript, or another parent process.

Production integration should therefore grant FDA only to a minimal stable broker, keep the GUI unprivileged, validate every candidate disk inside the broker, and remove `authopen/sys.openfile.*` from the final raw-device path.
